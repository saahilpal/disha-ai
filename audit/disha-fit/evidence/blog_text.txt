The Anatomy of a Voice AI Pipeline
The old way
For a really long time, voice AI pipelines followed the same structure: a cascaded pipeline made of an STT (speech-to-text) layer, an NLP layer (some sort of decision tree to capture intent and map it to a fixed response), and a TTS (text-to-speech) layer to finally respond back to the user.
These pipelines were too rigid, because they waited for the user to complete their entire utterance and then invoked speech-to-text, the LLM, and text-to-speech one after another. The delay of all three pieces cascaded, batched together.
If we want to reduce the overall response latency, we need a structure where we don't wait for one step to fully complete before invoking the next. Instead, we let each component in the pipeline continuously stream its output to the next for further processing.
Basic components of the modern pipeline
The modern voice AI pipeline continuously runs three parallel streams:
Audio input : voice activity detection (VAD) plus noise filtering.
Transcription : the STT outputs continuously updating text, but we wait for the  final  transcript before calling the LLM.
Response : the LLM streams its response, which is fed into TTS, ideally once a coherent sentence completes. If the user interrupts, start again. That sentence buffer is what gives the speech proper tone and pace.

Role and decisions of each component
Audio input
Send audio data in small chunks (ideally around 20 ms) and filter out background noise. Ideally you also run VAD (voice activity detection) in this layer to figure out whether someone is actually talking. We'll discuss the role of VAD in detail later.
Speech-to-text
Continuously takes the incoming audio as input and streams transcription text as output, ideally with markers for  interim  (not final, can still change) and  final  transcripts (safe to use definitively as LLM input). The interim transcript is what you use to interrupt the bot and stop its speech; the final transcript is what invokes the LLM turn.
LLM
The LLM request is a discrete request, since we can't continuously stream data  into  a text-based LLM. But we can stream its output token by token. This layer has one more responsibility: maintaining the context of the conversation as a list of user and assistant messages. There's some nuance in exactly which assistant messages get captured in that context, which we'll discuss later.
TTS
As the LLM response streams in, the TTS layer gathers it token by token and ideally sends it to the text-to-speech API websocket once a sentence is complete. The response, which is the generated audio, also comes back chunk by chunk, and is played sequentially. Ideally we can generate the audio for multiple sentences in parallel and queue them to be played back one after the other.

Code in a nutshell
A voice AI pipeline is really a few loops running concurrently, each listening for data and moving it one step along. The data moving between the individual steps is easiest to think of as  frames  (or packets). A frame can hold any data, like audio coming in from the user, audio generated by the TTS, or text generated by the LLM. Each step in the pipeline either generates frames of its own, manipulates the frames arriving from the previous step, or simply forwards them along.
The outline of such a step fits in a few lines of Python: a queue in, a queue out, and a loop between them.
@dataclass
class Frame:
kind: str                # "audio" | "text" | "control"
data: bytes | str
class Processor:
"""One step in the pipeline: consume frames, emit frames."""
def __init__(self):
self.inbox: asyncio.Queue[Frame] = asyncio.Queue()
self.next: "Processor | None" = None
async def process(self, frame):
yield frame          # default behavior: forward untouched
async def run(self):
while True:
frame = await self.inbox.get()
async for out in self.process(frame):   # generate / transform / forward
if self.next:
await self.next.inbox.put(out)
# wire the steps together: mic -> stt -> llm -> tts -> speaker
mic.next = stt
stt.next = llm
llm.next = tts
tts.next = speaker
# start all five loops; they run at the same time,
# each pulling frames in and pushing frames along
await asyncio.gather(mic.run(), stt.run(), llm.run(), tts.run(), speaker.run())
Each concrete step overrides  process : the STT step consumes audio frames and emits text frames, the TTS step consumes text frames and emits audio frames, and a noise filter just transforms audio frames and passes them on. Every connector you watched in the simulation above is one of these queues.
What latency matters at each stage
At every stage in the pipeline, the delay to stream the  first  piece of data is what dictates the final  speech-to-speech latency . This is the most important metric for the performance of a voice AI pipeline, measured from the moment the user stopped speaking to the moment the bot starts speaking.
Starting from the audio input: if we're using VAD, there's a fixed silence window we configure to decide that the user has stopped speaking. Set it too low and you'll eagerly interrupt the user; set it too high and the bot is slow to respond.
For the speech-to-text stage, if we're using VAD we can measure the time between using the VAD signal to finalize the transcript and actually receiving that final transcript. Without a VAD in the system, it's difficult to measure STT latency at all, unless the provider reports it themselves.
For the LLM layer, two metrics matter:  TTFT  (time to first token) and  TPS  (tokens per second), the first one being the most important. For text-to-speech, the key metric is  TTFB  (time to first byte).
Put together, the speech-to-speech latency measured at our server is:  VAD delay + STT finalization delay + LLM TTFT + TTS TTFB . Ideally, you should target keeping it under one second total.

Turn detection
So far we've covered the basic building blocks and how they interact. Now for the most important aspect of a voice AI pipeline, the one that can make or break the user experience:  turn detection . It means figuring out when the user has decided to  start  their turn (if the bot is speaking, it should be interrupted) and when the user has  stopped  their turn and is expecting a response from us.
The LLMs inside voice pipelines are text models built around turn-based communication: a user message, an assistant message, back and forth. A live conversation is a continuous stream of audio, so the pipeline has to impose that turn structure itself. Concretely, it needs to answer two questions:  when did the user's turn start , and  when did it stop .
Detecting that a turn has started
Plain VAD.  Start a user turn whenever a voice-activity model (like Silero) hears speech. The downfall: even small back-channel sounds like an "okay" or a "hmm" will stop the bot mid-sentence, which gets very annoying very fast.
Transcript-based.  Use the transcript in some manner instead: start the turn on any transcript at all, or gate it behind a phrase or a minimum word count, so noise and one-word acknowledgements don't count as a turn.
A custom model.  A dedicated model that takes the audio or the transcription as input and decides whether a real turn has started, e.g. Krisp VIVA.
Detecting that a turn has ended
This is usually harder and trickier than detecting the start, because there's a lot of nuance in how people actually talk. Someone reading out a phone number pauses between digit groups; someone thinking while speaking pauses mid-sentence. Three common approaches:
A fixed wait after VAD silence.  Simple, but it misses all of those pauses, and the timeout becomes a lose-lose knob: too short and the bot answers before the user finished the thought; too long and you're waiting that same amount after  every  utterance, so every response is slow. Handling LLM context in interruptions
Above, we discussed the techniques for detecting the start and end of a user turn. Now, if a user turn starts while we're in the middle of speech, the LLM should only see in its context, for the next turn, the text the user has  definitely heard : the part that was actually played. If we don't do this, the LLM believes everything it generated was heard. It will stop itself from repeating things, or assume context that was never actually discussed.
To do this effectively, we need to know which part of the transcript aligns with how far the audio playback actually got.
Mostly this is done by controlling the flow of text and audio frames and synchronizing them, so that we only store the part of the transcript the user has heard. The mechanism is  word timestamps , which come back from the text-to-speech provider. Your use case might be fine without this, but most real-world use cases do require this level of interruption handling.

Looking forward
The future might involve  speech-to-speech models , like GPT Live or GPT Realtime, which handle turn-taking, interruption handling, and context management much more naturally, along with text-based LLMs, which are good at tool calling and deeper thinking in the background. For now, though, these models are too expensive for real-world production scenarios at scale.
Conclusion
In this post we went through the basic components and structure of a voice AI pipeline: the streaming layers, the frames moving between them, where the latency hides, turn detection, and keeping the LLM's context honest through interruptions.
In future posts we'll build on this structure: integrating tool calling so the agent can fetch context it wasn't given up front, measuring the performance of a voice AI pipeline, and handling scaling and deployments.
